# 1.0 最小上线验收与版本排期

本计划用于管理异常访问监测组件从当前工程状态到 1.0 最小可上线版本的待办事项。排序原则是先满足“可接入、可审计、可回滚、可证明”的上线验收成果，再安排增强能力；不把动态规则热加载、完整前端 SDK、生产控制实现等非必要能力塞入 1.0。

## 版本目标

| 版本 | 目标 | 发布结论 |
| --- | --- | --- |
| 1.0.0-rc1 | 冻结公开契约并完成最小上线验收闭环 | 候选发布，用于预发与宿主试接入 |
| 1.0.0 | 通过最小上线验收、文档与构建证据齐备 | 首个可上线版本 |
| 1.1.x | 增强宿主接入体验与控制样例 | 1.0 后迭代，不阻塞上线 |
| 1.2.x | 规则动态化、管理端增强和高级治理 | 单独设计与验收，不纳入 1.0 |

## 建议节奏与依赖顺序

以下按一名工程师全职投入估算；宿主系统提供真实认证、控制服务、目标数据库和预发布环境的等待时间不计入。若由多人并行，仍必须保持“发布收口 -> 契约/持久化 -> Starter/安全 -> 宿主验收 -> 发布”的依赖顺序。

| 周期 | 目标版本 | 工作重点 | 完成门禁 |
| --- | --- | --- | --- |
| 第 1 周 | 1.0.0-rc1 | 发布分支收口、公开契约冻结、Schema/文档一致性、MyBatis 迁移复核 | 发布分支干净；api/core/web-contract/mybatis 测试通过 |
| 第 2 周 | 1.0.0-rc1 | Boot 2/3 Starter、集成审计项目、控制幂等和 OBSERVE/ENFORCE 保护 | 两个 Boot 最小宿主 HTTP 验收通过 |
| 第 3 周 | 1.0.0-rc1 | 前端补充信息宿主适配验收、模板与文档收口、预发布部署 | 以 OBSERVE 跑通事件、告警、控制候选与前端信号 |
| 第 4 周 | 1.0.0 | 修复 rc1 范围内缺陷、回归、发布说明、标签与组件发布 | 全量 Reactor 通过；已知限制、迁移与回退说明齐备 |

## 1.0 最小上线验收成果

1. 构建可证明：mvn clean verify -DskipTests=false 在干净发布分支通过，Surefire 报告可追溯。
2. 契约可冻结：api、core.port、web-contract 的公开类型、JSON Schema、配置元数据和 Maven 坐标稳定。
3. 接入可运行：Boot 2 与 Boot 3 最小宿主均可启动，并通过 HTTP 验收事件、告警、控制记录和 MyBatis 持久化结果。
4. 审计可落库：monitoring-schema.sql 覆盖事件、属性、角色、告警、控制、处置、规则版本和白名单，迁移说明清晰。
5. 安全边界可说明：身份、角色、源 IP、会话、授权结论和前端补充信息均有明确可信来源和禁止项。
6. 上线可回退：默认 OBSERVE，切换 ENFORCE 前必须验证宿主 ControlHandler 幂等和失败行为。
7. 文档可执行：README、集成指南、架构运维说明、领域模型、集成审计说明与 Javadoc 生成说明互相一致。

## 1.0 不纳入范围

- [ ] 不实现持久化动态规则 DSL 编译、热加载、灰度和回滚；仅保留管理模型和文档边界。
- [ ] 不提供生产级验证码、限流、账号锁定、会话撤销或 MFA 服务；仅提供契约、样例和验收要求。
- [ ] 不提供通用前端 SDK 或统一响应 JSON；前端接入由宿主后端适配。
- [ ] 不保证跨数据库的生产并发性能；1.0 只提供 H2/MyBatis 集成证据和迁移脚本。
- [ ] 不把组件事务并入宿主业务事务；跨资源一致性由宿主采用 outbox 或自有事务方案。
