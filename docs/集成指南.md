# 集成指南

本指南面向宿主系统开发者。推荐顺序是：选择 Starter、执行数据库迁移、实现宿主 SPI、以 `OBSERVE` 运行、验收后再启用 `ENFORCE`。完整运行边界与值守项见[架构与运维说明](架构与运维说明.md)。

## 1. 选择依赖与配置

| 宿主版本 | Starter | Servlet 命名空间 |
| --- | --- | --- |
| Spring Boot 2.7.x | `sys-abnormal-access-monitoring-spring2-starter` | `javax.servlet` |
| Spring Boot 3.x | `sys-abnormal-access-monitoring-spring3-starter` | `jakarta.servlet` |

不要同时引入两个 Starter。两者均使用 `abnormal.access.monitor` 前缀：

```yaml
abnormal:
  access:
    monitor:
      system-id: order-service       # 稳定且可追溯的系统标识
      mode: OBSERVE                  # OBSERVE 或 ENFORCE
      frontend:
        enabled: true
      trusted-proxies: [10.0.0.0/8]
```

`OBSERVE` 仍会记录事件、执行规则、生成告警，但不发起自动控制。`ENFORCE` 只有在至少注册一个可执行的 `ControlHandler` 时才能启动。`trusted-proxies` 仅包含实际受信任的反向代理；来自不受信任直连请求的转发头不能用于确定客户端 IP。

## 2. 实现宿主 SPI 与资源访问记录

用初始化插件生成 `HostMonitoringSpi.java` 与 `HostControlHandler.java`，移入宿主 `src/main/java` 后注册为 Bean。SPI 不依赖 Spring Security、Sa-Token 或具体权限框架。

| SPI | 宿主责任 |
| --- | --- |
| `IdentityContextProvider` | 从服务端已认证上下文取稳定用户 ID、账号类型、角色和会话哈希 |
| `ResourceScopeAuthorizer` | 调用宿主数据权限服务，返回资源级允许或拒绝结论 |
| `TrustedProxyResolver` | 仅在直连地址受信任时解析转发链 |
| `EventEnricher` | 仅补充已批准、非敏感的业务摘要字段 |
| `ControlHandler` | 实现验证码、限流、锁定、撤销会话、二次认证或拒绝操作，并按幂等键去重 |

资源访问使用 `ResourceAccessGuard.authorize(identity, resourceRequest)`。它把宿主授权结果记为标准事件，但监测写入失败不会改变原结论；授权器未配置、返回空结论或抛出异常时一律按拒绝处理。不要根据浏览器参数自行放行资源。

`ControlHandler` 必须按 `ControlCommand.getIdempotencyKey()` 去重，并且只声明实际可执行的动作。例如 `AUTH-02` 的限流目标是 `ip:<sourceIp>`，有效期为 30 分钟；`AUTH-01` 会请求验证码和限流。控制失败不得绕过既有认证与数据权限。

## 3. MyBatis 迁移与告警闭环

生产环境必须提供数据源和 `SqlSessionFactory`，并把 JAR 中的 `db/monitoring-schema.sql` 纳入 Flyway、Liquibase 或既有迁移流程。Starter 检测到 `SqlSessionFactory` 后注册 Mapper 与 `InstantTypeHandler`，使用 `MyBatisMonitoringRepository`；否则使用内存仓储，仅适合本地开发和测试。组件不会自动建表。

迁移包含 `security_event`、事件角色/属性表、`security_rule`、`security_alert`、`alert_event_link`、`control_action`、`alert_disposition` 和 `security_whitelist`。迁移账户需要建表建索引权限；运行账户只保留新增、查询和必要更新权限。

通过 `AlertLifecycleService` 进行 `acknowledge`、`startInvestigation`、`close` 或 `falsePositive`。每次状态转换都会追加 `alert_disposition`；原始安全事件不应被覆盖或删除。关闭告警需要证据摘要。

## 4. 前端信号契约

规范位于 `web-contract/src/main/resources/frontend-signal.schema.json`，当前版本为 `1.0`。必填字段是 `client_event_id`、`occurred_at`、`request_id`、`route` 和 `action`。`device_id_hash`、`resource_id_hash` 使用 `sha256:` 前缀；`attributes` 只允许 `feature`、`interaction`、`page_type`、`network_type`、`ui_version`、`resource_class`、`outcome_hint`。

宿主端点应先执行自身认证、请求体大小限制、频率限制和 JSON Schema 校验，再从服务端上下文创建 `FrontendServerContext`，调用 `FrontendSignalRecorder.record(signal, serverContext)`。客户端不得发送或断言用户、角色、源 IP、会话、风险等级、告警 ID、控制动作或最终授权结果。客户端时间仅是证据，不能替代服务端时间和身份判断。

## 5. 初始化插件

```powershell
mvn io.github.jasperbigsum-commits:sys-abnormal-access-monitoring-maven-plugin:${abnormal-access-monitoring.version}:initialize `
  '-Dabnormal.access.monitor.outputDirectory=src/main/resources/abnormal-access-monitoring' `
  '-Dabnormal.access.monitor.packageName=com.example.orders.monitoring' `
  '-Dabnormal.access.monitor.systemId=order-service'
```

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `abnormal.access.monitor.outputDirectory` | `${project.basedir}/src/main/resources/abnormal-access-monitoring` | 模板输出目录 |
| `abnormal.access.monitor.packageName` | `com.example.monitoring` | 生成 Java 模板的包名 |
| `abnormal.access.monitor.systemId` | `change-me` | 生成 YAML 中的系统标识 |

目标创建配置、`host-spi/HostMonitoringSpi.java`、`host-spi/HostControlHandler.java` 和 `frontend-signal-v1.example.json`。所有文件以 `CREATE_NEW` 写入，已有文件只会保留并在 Maven 日志中提示。

## 6. 升级与验收

升级组件前，先在预发布环境执行新迁移并用 `OBSERVE` 对照现有审计结果。由 Boot 2 升级至 Boot 3 时，替换 Starter、将宿主 MVC/Servlet 集成从 `javax.*` 迁移到 `jakarta.*`，并以 JDK 17 编译。变更规则阈值、控制 TTL、Schema 或 SPI 时，补充宿主验收用例并执行：

```bash
mvn clean verify -DskipTests=false
```
