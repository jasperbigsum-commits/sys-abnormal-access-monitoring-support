# 集成指南

本指南面向宿主系统开发者。推荐顺序是：选择 Starter、执行数据库迁移、实现宿主 SPI、以 `OBSERVE` 运行、验收后再启用 `ENFORCE`。完整运行边界与值守项见[架构与运维说明](架构与运维说明.md)。

## 1. 选择依赖与配置

| 宿主版本 | Starter | Servlet 命名空间 |
| --- | --- | --- |
| Spring Boot 2.7.x | `sys-abnormal-access-monitoring-spring2-starter` | `javax.servlet` |
| Spring Boot 3.x | `sys-abnormal-access-monitoring-spring3-starter` | `jakarta.servlet` |

不要同时引入两个 Starter。两者均使用 `abnormal.access.monitor` 前缀：

```yaml
abnormal:
  access:
    monitor:
      system-id: order-service       # 稳定且可追溯的系统标识
      mode: OBSERVE                  # OBSERVE 或 ENFORCE
      frontend:
        enabled: true
      trusted-proxies: [10.0.0.0/8]
```

`OBSERVE` 仍会记录事件、执行规则、生成告警，但不发起自动控制。`ENFORCE` 只有在至少注册一个可执行的 `ControlHandler` 时才能启动。`trusted-proxies` 仅包含实际受信任的反向代理；来自不受信任直连请求的转发头不能用于确定客户端 IP。

## 2. 实现宿主 SPI 与资源访问记录

用初始化插件生成 `HostMonitoringSpi.java` 与 `HostControlHandler.java`，移入宿主 `src/main/java` 后注册为 Bean。SPI 不依赖 Spring Security、Sa-Token 或具体权限框架。

| SPI | 宿主责任 |
| --- | --- |
| `IdentityContextProvider` | 从服务端已认证上下文取稳定用户 ID、账号类型、角色和会话哈希 |
| `ResourceScopeAuthorizer` | 调用宿主数据权限服务，返回资源级允许或拒绝结论 |
| `TrustedProxyResolver` | 仅在直连地址受信任时解析转发链 |
| `EventEnricher` | 仅补充已批准、非敏感的业务摘要字段 |
| `ControlHandler` | 实现验证码、限流、锁定、撤销会话、二次认证或拒绝操作，并按幂等键去重 |

资源访问使用 `ResourceAccessGuard.authorize(identity, resourceRequest)`。它把宿主授权结果记为标准事件，但监测写入失败不会改变原结论；授权器未配置、返回空结论或抛出异常时一律按拒绝处理。不要根据浏览器参数自行放行资源。

`ControlHandler` 必须按 `ControlCommand.getIdempotencyKey()` 去重，并且只声明实际可执行的动作。例如 `AUTH-02` 的限流目标是 `ip:<sourceIp>`，有效期为 30 分钟；`AUTH-01` 会请求验证码和限流。控制失败不得绕过既有认证与数据权限。

## 3. MyBatis 迁移与告警闭环

生产环境必须提供数据源和 `SqlSessionFactory`，并把 JAR 中的 `db/monitoring-schema.sql` 纳入 Flyway、Liquibase 或既有迁移流程。Starter 检测到 `SqlSessionFactory` 后注册 Mapper 与 `InstantTypeHandler`，使用 `MyBatisMonitoringRepository`；否则使用内存仓储，仅适合本地开发和测试。组件不会自动建表。

迁移包含 `security_event`、事件角色/属性表、`security_rule`、`security_alert`、`alert_event_link`、`control_action`、`alert_disposition` 和 `security_whitelist`。迁移账户需要建表建索引权限；运行账户只保留新增、查询和必要更新权限。

通过 `AlertLifecycleService` 进行 `acknowledge`、`startInvestigation`、`close` 或 `falsePositive`。每次状态转换都会追加 `alert_disposition`；原始安全事件不应被覆盖或删除。关闭告警需要证据摘要。

## 4. 前端信号契约

规范位于 `web-contract/src/main/resources/frontend-signal.schema.json`，当前版本为 `1.0`。必填字段是 `client_event_id`、`occurred_at`、`request_id`、`route` 和 `action`。`device_id_hash`、`resource_id_hash` 使用 `sha256:` 前缀；`attributes` 只允许 `feature`、`interaction`、`page_type`、`network_type`、`ui_version`、`resource_class`、`outcome_hint`。

宿主端点应先执行自身认证、请求体大小限制、频率限制和 JSON Schema 校验，再从服务端上下文创建 `FrontendServerContext`，调用 `FrontendSignalRecorder.record(signal, serverContext)`。客户端不得发送或断言用户、角色、源 IP、会话、风险等级、告警 ID、控制动作或最终授权结果。客户端时间仅是证据，不能替代服务端时间和身份判断。

## 5. 初始化插件

```powershell
mvn io.github.jasperbigsum-commits:sys-abnormal-access-monitoring-maven-plugin:${abnormal-access-monitoring.version}:initialize `
  '-Dabnormal.access.monitor.outputDirectory=src/main/resources/abnormal-access-monitoring' `
  '-Dabnormal.access.monitor.packageName=com.example.orders.monitoring' `
  '-Dabnormal.access.monitor.systemId=order-service'
```

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `abnormal.access.monitor.outputDirectory` | `${project.basedir}/src/main/resources/abnormal-access-monitoring` | 模板输出目录 |
| `abnormal.access.monitor.packageName` | `com.example.monitoring` | 生成 Java 模板的包名 |
| `abnormal.access.monitor.systemId` | `change-me` | 生成 YAML 中的系统标识 |

目标创建配置、`host-spi/HostMonitoringSpi.java`、`host-spi/HostControlHandler.java` 和 `frontend-signal-v1.example.json`。所有文件以 `CREATE_NEW` 写入，已有文件只会保留并在 Maven 日志中提示。

## 6. 前端补充信息统一接入

前端补充信息必须先到达宿主系统的后端 HTTP API，再由宿主适配后调用组件。组件统一接收、校验、规范化与记录功能，以及 `FrontendSignal` v1 的语义；组件不提供通用 Controller、不规定固定 URL、不实现认证，也不定义响应 JSON。宿主可推荐使用 `POST` 与 `application/json`；`/api/monitoring/frontend-signals` 仅是非规范性示例，实际路由、认证、响应模型和框架实现均由宿主负责。

组件的统一入口为 `FrontendSignalRecorder.record(signal, serverContext)`。浏览器提交的值仅是非权威的补充证据，不能替代服务端认证、授权或业务判定。

宿主可以继续使用自己的原生请求 DTO，但必须做显式、逐字段映射：`pageCode -> route`、`operationCode -> action`、单向哈希后的订单 ID `-> resource_id_hash`。未映射的业务字段不得放入 `attributes` 或任意扩展 payload。要发布新字段时，必须同时更新 Schema、`FrontendSignal` 白名单、测试和本文档。

### 6.1 标准请求契约与字段映射

标准 Schema 位于 `web-contract/src/main/resources/frontend-signal.schema.json`，当前版本为 `1.0`。以下字段均来自浏览器，除明确由服务器验证或派生的关联信息外，均只能作为非权威补充证据。

| 字段 | 必填 | 映射规则 | 信任级别 |
| --- | --- | --- | --- |
| `contract_version` | 否，存在时必须为 `1.0` | 原样映射；未提供时 v1 默认按 `1.0` 处理 | 非权威补充证据 |
| `client_event_id` | 是 | 浏览器为一次前端事件生成的 UUID 或等价唯一标识 | 非权威补充证据 |
| `occurred_at` | 是 | 浏览器事件时间，解析为 UTC 时间戳 | 非权威补充证据，必须做时钟偏差校验 |
| `request_id` | 是 | 关联宿主服务器已签发或可验证的请求标识 | 非权威关联证据；不建立任何身份 |
| `trace_id` | 否 | 映射宿主允许前端回传的链路关联标识 | 非权威补充证据 |
| `route` | 是 | 原生 DTO 的 `pageCode` 显式映射为稳定路由语义 | 非权威补充证据 |
| `action` | 是 | 原生 DTO 的 `operationCode` 显式映射为稳定操作语义 | 非权威补充证据 |
| `device_id_hash` | 否 | 仅映射经单向哈希的设备标识 | 非权威补充证据 |
| `resource_type` | 否 | 映射受控的资源类别，例如 `order` | 非权威补充证据 |
| `resource_id_hash` | 否 | 单向哈希后的订单 ID 等业务资源标识显式映射至此 | 非权威补充证据 |
| `attributes` | 否 | 仅映射已发布的低风险交互属性 | 非权威补充证据 |

`device_id_hash` 与 `resource_id_hash` 出现时都必须以 `sha256:` 开头。`attributes` 仅允许 `feature`、`interaction`、`page_type`、`network_type`、`ui_version`、`resource_class`、`outcome_hint`；对象及其嵌套 `attributes` 均由 `additionalProperties=false` 拒绝未知字段。`request_id` 必须关联到服务器已签发或可验证的请求，但它不建立用户、会话或任何身份。

```json
{
  "contract_version": "1.0",
  "client_event_id": "fd584fda-3d98-4e73-857f-a19e3be1e456",
  "occurred_at": "2026-07-23T09:30:00Z",
  "request_id": "req-5af1f1f0",
  "trace_id": "trace-41c92bd9",
  "route": "/orders/detail",
  "action": "order:view",
  "resource_type": "order",
  "resource_id_hash": "sha256:6a440d8653c80e2176c0f59ec1d4c572e0ebd4b4667c491505c9067cfde2a8c4",
  "attributes": {
    "feature": "order-center",
    "page_type": "detail",
    "ui_version": "2026.07"
  }
}
```

浏览器不得提交或断言用户 ID、角色、账户类型、会话 ID、来源 IP、风险等级、告警 ID、控制动作、授权决定或最终业务结果。这些信息只能来自宿主已认证上下文、可信代理配置或服务器侧业务处理。

### 6.2 宿主接口适配流程

下面是伪代码。`HostFrontendSignalRequest`、`HostAuthenticationContext`、Schema 校验器、接入限流器、映射函数和响应工厂均为宿主自有类型；示例路径也不构成组件的固定端点。

```java
// 伪代码：路径、DTO、认证类型、校验器、限流器、映射函数和响应工厂都由宿主系统定义。
@PostMapping(
        path = "/api/monitoring/frontend-signals",
        consumes = MediaType.APPLICATION_JSON_VALUE)
public Object receiveFrontendSignal(
        @RequestBody HostFrontendSignalRequest request,
        HostAuthenticationContext authenticationContext,
        HttpServletRequest httpRequest) {
    // 控制器前的安全链已完成认证和端点授权；Cookie/会话认证必须先完成 CSRF 防护。
    // 若支持跨源浏览器访问，宿主另行配置明确的 CORS 来源白名单和凭据策略；CORS 绝不替代 CSRF。

    String trustedSourceIp = trustedProxyResolver.resolveClientIp(
            httpRequest.getRemoteAddr(), httpRequest.getHeader("X-Forwarded-For"));
    // 可信来源 IP 仅由 TrustedProxyResolver 解析，阻止浏览器伪造转发头绕过基于 IP 的防护。
    HostIngressRateLimitResult rateLimit = hostIngressRateLimiter.check(
            authenticationContext.getTrustedUserOrSessionKey(), trustedSourceIp);
    // 宿主限流器同时以已认证用户或会话与可信 IP 为键，先限制恶意流量再消耗 Schema 或映射资源。
    if (!rateLimit.isAllowed()) {
        // 拒绝必须立即停止处理，并由宿主自己的响应工厂返回 HTTP 429。
        return hostTooManyRequestsResponse();
    }

    hostFrontendSignalSchemaValidator.validate(request);
    // Schema 拒绝未知字段和不支持版本；原始请求体、Cookie、令牌和业务实体绝不写入监控事件。

    FrontendSignal signal = FrontendSignal.builder()
            .contractVersion(request.getContractVersion())
            .clientEventId(request.getClientEventId())
            .occurredAt(request.getOccurredAt())
            .requestId(request.getRequestId())
            .traceId(request.getTraceId())
            .route(mapPageCodeToRoute(request.getPageCode()))
            .action(mapOperationCodeToAction(request.getOperationCode()))
            .deviceIdHash(request.getDeviceIdHash())
            .resourceType(mapResourceType(request.getResourceType()))
            .resourceIdHash(hashOrderIdOneWay(request.getOrderId()))
            .attribute("feature", request.getFeature())
            .attribute("page_type", request.getPageType())
            .attribute("ui_version", request.getUiVersion())
            .build();
    // 原生 DTO 只通过显式映射进入 FrontendSignal，由其强制长度、哈希前缀和 attributes 白名单。

    Instant receivedAt = clock.instant();
    frontendSignalValidator.validate(signal, receivedAt);
    // clock.instant() 是权威接收时间；FrontendSignalValidator 的时钟偏差失败应由宿主转换为 HTTP 400。

    FrontendServerContext serverContext = FrontendServerContext.builder()
            .sourceIp(trustedSourceIp)
            .userId(authenticationContext.getAuthenticatedUserId())
            .sessionIdHash(authenticationContext.getTrustedSessionIdHash())
            .accountType(authenticationContext.getAccountType())
            .roleIds(authenticationContext.getRoleIds())
            .build();
    // 用户、角色和会话哈希只从已认证上下文派生，IP 复用上方 TrustedProxyResolver 得到的可信值。

    frontendSignalRecorder.record(signal, serverContext);
    // 记录器将前端补充证据与可信服务器上下文合并，供组件后续规则处理。
    return hostSuccessResponse();
    // 成功响应保持为宿主自己的 API 模型，组件不提供任何响应 JSON。
}
```

处理顺序必须严格为：认证和端点授权 -> Cookie/会话认证时的 CSRF 防护 -> 若支持跨源浏览器访问，单独执行明确的 CORS 来源白名单和凭据策略（CORS 绝不替代 CSRF） -> JSON `Content-Type` -> 请求体大小限制 -> 对可信用户和可信 IP 限流 -> JSON Schema -> `FrontendSignal` 构造校验 -> 时钟偏差 -> 可信服务器上下文 -> `FrontendSignalRecorder.record`。只有直接来源已被信任时，且仅可由 TrustedProxyResolver 解释转发请求头。

### 6.3 响应语义、重试与验收

组件不提供响应 JSON、错误码或异常包装器。宿主保留自己的 API 响应体；HTTP 语义建议如下：无效 JSON、未知字段、不支持的契约版本、对象校验失败或时钟偏差为 `400`；未认证为 `401`；无权访问为 `403`；请求体过大为 `413`；触发限流为 `429`；不可恢复的内部错误为 `5xx`。错误响应不得回显完整事件、Cookie、会话值、规则、风险分数、告警详情或控制信息。

宿主可选用短期去重键：`可信用户或会话范围 + client_event_id`。该组件不提供端到端去重；重试、幂等窗口和最终响应语义仍由宿主 API 决定。

| 验收场景 | 期望结果 |
| --- | --- |
| 标准提交 | 通过 Schema、构造校验和时钟偏差校验后，以可信服务器上下文调用 `FrontendSignalRecorder.record`。 |
| 原生 DTO 映射 | `pageCode`、`operationCode` 和单向哈希订单 ID 分别明确映射到 `route`、`action`、`resource_id_hash`，未映射业务字段不被记录。 |
| 未知字段 | 顶层或 `attributes` 中存在未发布字段时，由 `additionalProperties=false` 拒绝并返回宿主 `400`。 |
| 时钟偏差 | `occurred_at` 超过允许偏差时，不调用记录器，宿主返回 `400`。 |
| 身份/IP/角色伪造 | 浏览器声明被忽略或拒绝；身份、角色和 IP 仅从认证上下文及可信代理配置派生。 |
| 重复 `client_event_id` | 在宿主配置的短期去重窗口内，按可信用户或会话范围处理；组件不承诺端到端去重。 |
| 限流 | 基于可信用户与可信 IP 执行限流，超过阈值时宿主返回 `429`，不进入记录器。 |
